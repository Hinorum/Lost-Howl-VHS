# The Ways — LOST HOWL

Фанатский Telegram-бот по мотивам Lost Dogs: The Way — не связан с официальной командой, использует только общие мотивы и собственные имена.

Бот — это **видеомагнитофон LOST HOWL** в Telegram: раз в месяц Хранитель ставит в лоток **кассету** — рукописный фанфик-продолжение (стая псов ищет дом в разрушенном городе). Каждый день игроки выбирают **один из трёх черновиков кадра** кнопкой под постом дня; закон дня (большинство / меньшинство / середина) честной энтропией решает, какой кадр уцелеет и напишет канон дня. Поверх сюжета — **блокчейн-экономика** (Gram, бывший TON): исход дня решают банки ставок, бесплатные голоса ведут лидерборд, а верные пути копят Следы и копилки. Вся механика заточена под честный подсчёт, выплаты и копилки; внешних платных API нет.

## LOST HOWL — что это

**Стая** — игровое сообщество бота. У бота нет своего мира: он плеер, а сценарий — кассеты-фанфики, которые пишет и ставит в лоток **Хранитель** (месяц = кассета, файлы в `app/story/cassettes/`). Плёнка нарезана на кадры: заголовок главы, живая сцена (текст дня) и развилка из трёх черновиков кадра. Кассета умеет «перематываться»: если в день `D` уцелел определённый кадр, с дня `D+1` и до конца месяца играется ответвление сюжета; невыбранные кадры в сценарий больше не возвращаются. Канон дня (что именно произошло) звучит в итогах адресно победившим кадром. За миром следит **Хранитель**: ведёт казну, разбирает споры, держит стоп-кран, выбирает кассету месяца.

## Как устроен день

Сутки Стаи заякорены на UTC (по умолчанию день открывается в 11:00 UTC, голосование закрывается в 11:00 UTC следующего дня):

1. **Открытие дня** — пост: заголовок главы, живая сцена кассеты (текст дня) и развилка из трёх черновиков кадра (`Путь I/II/III` — название и короткое описание каждого). Закон дня объявлен сразу, банки ставок скрыты. Выбор — кнопкой под постом или кнопками пульта.
2. **Выбор пути** — один голос на игрока в сутки (`INSERT` с уникальностью `(round_id, player_id)`). Бесплатный голос ведёт лидерборд игрока, но на исход дня не влияет: решающий счёт — суммы подтверждённых ставок Gram на каждом пути.
3. **Закрытие и подсчёт** — мгновенный: `SUM(ставок) GROUP BY card_position`, побеждает путь по закону дня. День, на который не поставлено ни одного Gram, решается голосами.
4. **Итоги и новый день** — приходят в чаты сразу: канон дня (текст уцелевшего кадра), голоса, очки и выплаты; при «перемотке» кассеты с нового дня играется ответвление сюжета. Тяжёлая часть (выплаты, копилки) уходит фоном.

Три закона дня применяются к **банкам путей**: **большинство** (побеждает путь с большим весом ставок), **меньшинство** (с меньшим), **медиана** (средний по счёту). Закон дня выводится из **энтропии мастерчейна** — `root_hash % 3` последнего блока TON в момент открытия дня (как жребий при ничьей): блок в цепочке до начала голосования, подогнать закон задним числом нельзя (номер блока и `root_hash` хранятся в записи дня и доступны хранителю; в сообщения игроков они не печатаются). Закон **публичен с первой минуты** — никаких скрытых правил: игроки делают выбор, зная, что сегодня решает. В день без ставок те же законы применяются к бесплатным голосам.

### Проверка закона дня

Закон объявляется публично в анонсе дня — скрытых правил нет. Блок-источник и его root_hash хранятся в записи дня (колонка `rule_entropy`, формат `seqno:root_hash`) и доступны хранителю; в сообщениях игроков они не печатаются. Проверка занимает пару минут:

1. Узнай у хранителя (или из БД) номер блока и `root_hash` — 64 hex-символа.
2. Открой страницу блока в эксплорере, например `https://tonviewer.com/block/-1:8000000000000000:85601844`, и сверь поле **Root hash**.
3. Посчитай `root_hash % 3` (0 = большинство, 1 = меньшинство, 2 = медиана):
   ```python
   int("…root_hash…", 16) % 3
   ```
4. Сверь результат с законом дня — они должны совпасть дословно. Блок запаян валидаторами и лежит в цепочке до открытия дня, поэтому его хеш нельзя подогнать под голосование задним числом.

### Проверка жеребьёвки ничьей

Ничья (равные суммы ставок на путях) решается тем же блоком TON. В пост итогов печатаются номер блока, хвост `root_hash` и ссылка на страницу блока в эксплорере. Победитель — **последняя hex-цифра `root_hash` по модулю числа претендентов**:

1. Открой ссылку из поста (`https://tonviewer.com/block/-1:8000000000000000:<seqno>`), сверь **номер блока** и хвост **Root hash**.
2. Возьми последнюю цифру `root_hash` и подели по модулю числа путей-кандидатов (0 = первый из них, 1 = второй):
   ```python
   int("…root_hash…"[-1], 16) % len(пути_кандидаты)
   ```
3. Сверь с указанными в посте сценами.

Блок существует до закрытия дня — подогнать жребий задним числом нельзя.

Вручную день можно закрыть раньше командой `/advance` (только админы из `ADMIN_IDS`). Стейки и выплаты — по UTC-сетке, без привязки к онлайн-статусу бота.

## Экономика дня (Gram = бывший TON)

Игра бесплатна; ставки включаются флагом `TON_ENABLED=true`. Игрок привязывает кошелёк (`/wallet`) и в течение дня переводит **нативную монету Gram** на казначейский кошелёк — это и есть ставка на выбранный путь.

- Одна ставка на игрока в день, минимум `STAKE_MIN_TON` (по умолчанию 0.5 Gram), верхней границы нет. Перевод токенов (USDt, NOT и пр.) ставкой не становится — watcher пропускает jetton-уведомления.
- Watcher раз в минуту читает входящие транзакции казначея через **TonAPI** (фолбэк — **Toncenter** при деградации), курсор хранится в БД: простой сервиса не теряет переводы, хвост догоняется за пару циклов. Ставка подтверждается по отправителю, поэтому форма адреса (UQ/EQ) и memo не важны.
- Исход дня по ставкам включается флагом `WINNER_BY_STAKES=true` (по умолчанию): закон дня применяется к суммам Gram, путь без ставки участвует как 0 Gram. При `false` исход дня всегда по бесплатным голосам (прежний режим; день без ставок решается голосами в любом случае).
- Фонд дня = сумма подтверждённых ставок. Если на победивший путь кто-то поставил:
  - **96%** — поставившим на верный путь, пропорционально ставкам (комиссия сети вычитается заранее, приз приходит «чистыми»). Если кто-то из поставивших пришёл по личной ссылке игрока (механика `/invite`, `REFERRAL_SECRET`), с таких ставок ещё **1%** уходит в копилку пригласившего, а не в пул победителей — доля победителей того дня падает (в пределе до ~95%);
  - **1%** — в Фонд Стаи (`PACK_FUND_PCT`, накопление, раздача вручную);
  - **2%** — в копилку недели (в понедельник её делят топ-3 недели);
  - **0,5%** — хранителю (`OWNER_RAKE_PCT`);
  - **0,5%** — в копилку месяца (1-го числа топ-3 месяца).
- Если на победивший путь не поставил никто — все ставки возвращаются игрокам без рейка и копилок (с вычетом газа сети). Отклонённые лимитами, неподтверждённые и «чужие» переводы попадают в очередь авто-возврата — деньги не оседают в казне молча.
- Мелкие доли (< `MIN_PAYOUT_GRAM`) не превращаются в дохлые переводы — капают в копилку недели. Идемпотентность по хешу транзакции и мемо защищают от задвоения выплат; статус «взята в работу» фиксируется до вещания — падение сервиса не ведёт к двойной оплате.

### Блокчейн-контур выплат

- **Диспетчер** раздаёт призы и возвраты: батч на ОДНОМ `get_seqno()` (два подряд перевода не получают одинаковый seqno — иначе один молча теряется), идемпотентность по memo комментарию.
- **Глубокая сверка истории казначея**: memo исходящих читается не одной страницей (128 tx), а страницами вглубь (до `PAYOUT_RECONCILE_MAX_PAGES`, окно `PAYOUT_RECONCILE_HISTORY_SECONDS` ≈ неделя, шаг с перекрытием 16 записей — memo на стыке страниц не теряется). TonAPI → фолбэк Toncenter.
- **Сверка «по требованию»**: когда сверять нужно конкретные memo (sent-выплаты без реального хеша), пагинация останавливается сразу после нахождения всех целей — слепого прохода до конца окна нет, меньше запросов к провайдеру.
- **Анти-дубль повтора**: повтор выплаты с `attempts > 1` при НЕдоступной истории замораживается — переотправка без возможности проверить memo = риск задвоить уже ушедший перевод. «Провайдеры молчат» и «переводов нет вообще» различимы.
- **Сверка «sent»** каждые 120с: memo из истории пишутся как реальный хеш; memo без подтверждения после `PAYOUT_CONFIRM_TIMEOUT_SECONDS` (20 мин) возвращаются в очередь — потерянный при гонке двух быстрых переводов приз переотправляется сам.
- **Общий HTTP-клиент** с пулом keep-alive соединений между циклами watcher/диспетчера и экспоненциальный backoff ретраев; «мёртвые» входящие ротируются по `STUCK_RETENTION_DAYS`.
- `/blockchain` — аудит-отчёт блокчейн-контура для разбора «куда делось»: история казначея, сверщики, наши исходящие, стuck-входящие.

### Зеркало казны: сверка «в ноль»

Баланс казначея считается дважды: свёркой БД (с допуском на оценку газа) и **зеркалом цепочки** — независимой копией каждой транзакции кошелька (весовой `treasury_mirror.py`, таблица `treasury_moves`). Тождество построением: баланс кошелька = Σ `balance_delta` его транзакций от генезиса до головы цепочки, поэтому зеркало сверяется с живым балансом **без допуска** (реальная комиссия берётся из цепочки — `total_fees`, а не из оценки):

- **Синк** (`sync_treasury_mirror`): бутстрап спуском от головы вглубь до дна истории провайдера, затем инкремент к голове. TonAPI → фолбэк Toncenter; каждая страница коммитится отдельно — краш не теряет прогресс. Идемпотентно по `tx_hash` (при реорганизации строка перезаписывается).
- **Диагностика** — строки `unknown_in` / `unknown_out` (пыль, jetton, ручные переводы) не мажутся по допуску, а честно показываются в `/treasury`, как и реальная сумма газа.
- **Автосверка**: каждый готовый цикл синка пишет проверку тождества «Σ движений = баланс цепочки» в `watcher_state` (`treasury_mirror_check`); `check_anomalies` раз в сутки будит хранителя, если расхождение не ноль или индексаторы молчат. Управляется `TREASURY_MIRROR_INTERVAL_SECONDS` (цикл синка) и `TREASURY_MIRROR_MAX_PAGES_PER_SYNC` (объём одного цикла).
- **Пополнение казны**: перевод владельца с кошелька `OWNER_WALLET_ADDRESS` и комментарием `bank:…` — не ставка и не возврат: деньги остаются в казне навсегда и учитываются зеркалом как входящий доход (`in:bank`). Так вносят внешний капитал, когда «банка» дня больше реального баланса кошелька (после тестов, возвратов и газа). С чужого кошелька мемо `bank:` привилегией не работает — штатный возврат/ставка.

### Смена выбора — платно

Один голос в день, но передумать можно за **Telegram Stars** или **Gram** с memo (`/change` в личке, `REVOTE_STARS` / `REVOTE_TON`). Грант сгорает вместе с днём.

### Копилки недели и месяца

Каждый день 2% фонда капает в копилку недели: в понедельник её делят **топ-3** прошедшей недели по числу верных путей (совпадений голоса игрока с победившей тропой) 50/30/20. Копилку месяца (0,5% в день) топ-3 забирают 1-го числа. Для призового места нужен привязанный кошелёк и минимум `WEEKLY_MIN_DAYS` дней голосования за период (анти-мультиаккаунт). Доля без достойного игрока переносится в следующий период. Живые таблицы — в `/top`.

## Команды игрока

- `/start`, `/help` — онбординг и памятка (с «пультом» кнопками)
- `/menu` — пульт LOST HOWL: сегодня, счёт, место, кошелёк, ставка, копилки, фонд, обновления — всё по кнопкам
- `/today` — кадр дня: глава кассеты живым текстом и три пути
- `/score`, `/rank` — твои пути и место в стае
- `/invite` — личная ссылка для приглашения (по желанию, `REFERRAL_SECRET`)
- `/change` — платная смена выбора
- `/wallet`, `/stake` — привязка кошелька и постановка ставки Gram (если включены ставки)
- `/top` — копилки и лидеры
- `/fund` — Фонд Стаи: накопление и правила раздачи

Бот запоминает чаты, куда его добавили администратором (группы и каналы), и сам шлёт туда каждый день итоги и новый день. Никаких команд для рассылки не нужно; удаление бота из чата останавливает доставку.

## Команды хранителя (только `ADMIN_IDS`, личные сообщения)

- `/advance` — закрыть день и открыть следующий
- `/resetgame confirm` — полный сброс игры (со счётами/ставками повторить копилки не даёт)
- `/panel` — пульт управления одной кнопкой (день, банк, очередь выплат, watcher, пауза, кассета месяца: выбрать `STORY_CASSETTE_NEXT_KEY` или спрятать сюжетный слой)
- `/ops` — пульт наблюдаемости: тот же список тревог, что уходит в личку, плюс возраст тика, проверок и watcher'а, очередь и падения тика подряд
- `/pause [причина]` / `/resume` — стоп-кран игры; входящие переводы на паузе автоматически возвращаются
- `/treasury` — здоровье казначея одним сообщением (+ блок «Зеркало казны» с тождеством Σ движений = баланс цепочки)
- `/blockchain` — аудит блокчейн-контура (история казначея, сверка, наши исходящие, stuck)
- `/adjust` — сверка казны с БД и закрытие расхождений
- `/payouts`, `/payout <id> retry|spam`, `/return`, `/fundout`, `/fund`, `/stakes`, `/incoming`, `/revenue` — очередь выплат, журнал входящих и выручка
- `/dispute`, `/disputes` — разбор формальных жалоб на итоги дней

## Наблюдаемость и надёжность

- `/health` — живой снимок: возраст последнего тика планировщика, сердцебиение watcher'а, очередь выплат, мёртвые письма, список текущих тревог (`problems`) и его возраст (`problems_age`), число падений тика подряд (`tick_failures`). Снимок и `/metrics` требуют авторизации: `HEALTH_TOKEN` передаётся в `Authorization: Bearer` либо в `?token=`.
- `/alive` — живость процесса **без токена и без снимка**: 200 значит только «отвечает». Это `healthCheckPath` в `render.yaml` (проба Render идёт без заголовков), поэтому секрет больше не нужно держать в манифесте: `HEALTH_TOKEN` живёт только в env Render, а `/alive` не отдаёт ни очереди выплат, ни тревог.
- **Аномалии сами находят админа**: watcher не завершает циклы, очередь выплат стоит, появились мёртвые письма — личное сообщение (троттлинг раз в час). Проверки идут джобой `ops-sweep` раз в 120с при любой конфигурации TON, а её вердикт кэшируется: `/health` и `/ops` читают один и тот же снимок и не ходят в сеть.
- **У аномалий есть конец и возраст**: когда проблема уходит, приходит «✅ ушла сама» (сколько держалась) и сбрасывается её кулдаун — повторное нарушение слышно сразу, а не через час. Затянувшееся состояние собирается в одну часовую сводку «держится N» вместо потока одинаковых сообщений по каждой проверке. В `/ops` и `/health` у тревог видно, сколько они держатся (`problem_details`).
- **Падение главного тика видно**: биение ставится только успешным тиком (иначе падающий цикл подтверждал бы собственную живость), счётчик падений и тревога с третьего подряд — в личку, кулдаун час.
- Сбой обработки апдейта не теряется молча: игрок получает «не получилось», хранителю уходит причина вместе с uid, чатом, типом апдейта и `update_id` — по ним же ищется в логах.
- **Self-ping** `/health` раз в `SELF_PING_SECONDS` — free plan Render не засыпает, и день открывается по UTC-сетке.
- `/metrics` — те же числа в текстовом формате Prometheus (`way_`), плюс то, чего раньше не измерялось вообще: запуск, результат и длительность каждой фоновой задачи (`way_job_runs_total`, `way_job_duration_seconds`) и сбои апдейтов по типу (`way_update_errors_total`). Учёт ведётся в памяти процесса (без новых зависимостей) и обнуляется на рестарте; недоступный снимок БД — это `way_snapshot_up 0` и 200, а не 500.
- **Молчание всегда с причиной**: `except: pass` в `app/` либо пишет в лог, либо объяснён комментарием рядом (тест `tests/test_silent_exceptions.py` не даёт добавить новое молчание незаметно). Раньше четыре «тихих» места в пульте могли показать здоровое состояние, которого нет.
- **Ежедневный бэкап** в `data/backups/` (04:17 по Москве, хранится 7 копий): SQLite — backup-API, Postgres — `pg_dump`.
- Схема — в моделях (`app/models.py`), история изменений — в `migrations/`. **Единственный источник правды о схеме — Alembic:** на старте рантайм сам приводит базу к `head` (`alembic upgrade head`); свежая база собирается из моделей и штампуется на `head`, легаси-базы create_all-эпохи без alembic-истории конвергируются в таймлайн идемпотентной ревизией `legacy_convergence`. Смена существующих таблиц — `alembic revision --autogenerate` → `alembic upgrade head`; миграции обязаны быть идемпотентно-применимыми. Осиротевшие `NOT NULL`-колонки удалённых механик дропаются только флагом `DROP_ORPHAN_COLUMNS=true` (разовый деплой), иначе — только предупреждение в логах.

## Деплой и миграции

Перед выкатом версии, меняющей схему, прогнать миграции на целевой базе вручную — до старта бота:

```bash
python -m alembic upgrade head
python -m alembic check    # «No new upgrade operations» — модели синхронны с head
```

Или одной командой через обёртку (читает `.env`/`DATABASE_URL`, прогоняет оба шага в правильном порядке):

```bash
python -m scripts.check_db
```

Удобно локально: на свежей БД `alembic check` без `upgrade head` валит «Target database is not up to date» — это не баг проекта, а сигнал, что схема не накатывалась.

Для Postgres сделать резервный `pg_dump` перед первым `upgrade head`. В CI те же шаги гоняются на обоих диалектах: джоба «Alembic drift check» — на свежей SQLite, джоба `test-postgres` — на PostgreSQL, где дополнительно проверяется весь flow миграций (см. ниже).

Что делает старт бота:

- **Свежая база** — схема собирается из моделей (`create_all`), `alembic_version` штампуется на `head`; последующий `upgrade head` — no-op.
- **База, ведущаяся alembic** — `alembic upgrade head` по своему таймлайну.
- **База create_all-эпохи без alembic-истории** — автоматическая реконсиляция: таблицы дотягиваются по моделям, история штампуется на якорь `a7b8c9d0e1f2`, затем база сходится ревизией `legacy_convergence` и хвостом истории. Хвост обязан быть переигрываемым (create_all уже собрал эти таблицы и снял эти колонки), иначе реконсиляция падала бы ровно на базах, ради которых написана. В логах должно появиться `Легаси-база конвергирована в alembic-таймлайн` — после этого прогнать `alembic check` лишний раз.

Осиротевшие `NOT NULL`-колонки удалённых механик: если в стартовых логах предупреждение `Найдены осиротевшие NOT NULL-колонки` — включи `DROP_ORPHAN_COLUMNS=true` на один деплой (колонки дропнутся, INSERT новых дней перестанет падать) и верни в `false`. Постоянно `true` не держать: при откате версии дроп снесёт колонку, нужную старому коду.

### Локальная проверка flow

`tests/test_migrations_flow.py` гоняет сам flow на временных базах, а не на рабочей: цепочка с нуля до `head` против моделей, идемпотентность повторного `upgrade`, откат `downgrade base` и обратный подъём, no-op `init_db` на базе, уже ведущейся alembic, и три сценария без истории — текущие модели без `alembic_version`, геометрия якоря без истории и база, которую оставила упавшая реконсиляция (create_all применён, история встала на якорь). Последний — это состояние бота, не смогшего стартовать: следующий запуск обязан долечиться сам и оставить чистый `alembic check`, как и обещает этот раздел.

Тот же flow прогоняется и на Postgres — на живой базе, а не на SQLite-файлах. Нужен `TEST_POSTGRES_URL` с суперпользователем: каждый тест создаёт свою одноразовую базу и снимает её с сервера на финише, поэтому имя общего `DATABASE_URL` тут не годится (общая база означала бы зависимость от порядка тестов). Без переменной PG-проверки молча пропускаются, а не падают:

```powershell
$env:TEST_POSTGRES_URL = "postgresql://postgres:...@localhost:5432/postgres"
python -m pytest tests/test_migrations_flow.py -q
```

Джоба `test-postgres` в CI задаёт эту переменную, так что после каждого пуша цепочка проверяется на том же диалекте, что и прод (Supabase Postgres). Версии в точности совпадать не могут: в CI это `postgres:16`, а мажорная версия прод-БД нигде не зафиксирована — при апгрейде провайдера диалект может поехать незамеченным, это стоит держать в голове. Именно так и нашёлся поломленный `downgrade base`: ревизии `2d4f3fbc1a33` и `4c9c12b66c56` в ветке отката пересоздавали колонки через `sa.DATETIME()`, а такого типа в Postgres нет (SQLite такой тип терпит молча, поэтому локально откат проходил). Правка — только в `downgrade()`: ветки `upgrade()` не тронуты, и этот DDL на Postgres никогда не выполнялся успешно, так что ни одна существующая база от правки не меняется.

Одно расхождение между схемой цепочки и моделями закреплено осознанно: `rounds.referral_nanotons` ревизия `a7b8c9d0e1f2` создаёт с `server_default=0`, а модель объявляет только питоновский `default=0`. На живых базах (create_all) серверного дефолта нет, ORM значение подставляет сам, поведение одинаковое; `rounds` ради косметики не переписываем. Список живёт в `KNOWN_DIVERGENCES` теста: новое расхождение валит тест, исчезновение старого — тоже. Учти, что на Postgres это расхождение для alembic **невидимо**: не-строковые server defaults он не сравнивает. Поэтому «чистый `alembic check` на PG» сам по себе ничего не говорит про эту колонку, и проверяет её отдельный тест — что ORM действительно пишет такую строку.

### PostgreSQL: что проверяется, а что нет

На Postgres сейчас проверяется **цепочка миграций и дрейф схемы** — это то, ради чего джоба и появилась, и именно этим ловились реальные баги (`sa.DATETIME()` в откате). Весь набор тестов приложения на Postgres **не гоняется сознательно**, и это не «всё зелено, просто не гоняли»: 66 тестов в 18 модулях падают на живом Postgres, а на SQLite проходят.

Причина одна и она не в приложении: тесты вставляют строки с захардкоженными внешними ключами, не создавая родителей, — например `payouts` со ссылкой на игрока `42`, которого в базе нет. SQLite внешние ключи по умолчанию **не проверяет**, поэтому такой сид годами проходил молча, а Postgres честно отвечает `ForeignKeyViolationError`. Затрачены `test_payout_dedupe`, `test_bank_refresh`, `test_ops`, `test_payout_confirm`, `test_ton`, `test_scheduler`, `test_payout_reconcile`, `test_admin_panel`, `test_chain_guards`, `test_day_lifecycle`, `test_incoming_ledger`, `test_money_mode`, `test_ops_diagnostics`, `test_refinalize_guard`, `test_revote`, `test_broadcast`, `test_payout_console`, `test_personal_results`.

Чтобы вернуть полный набор на Postgres, нужно чинить тестовые данные в этих модулях (создавать родительские строки перед вставками), а не отключать проверку внешних ключей: последнее сделает джобу зелёной ценой того самого, ради чего она есть. Пока задача не сделана, джоба `test-postgres` гоняет `tests/test_migrations_flow.py`, а основная джоба `test` остаётся полной на SQLite. Два других отличия Postgres, из-за которых этот набор и нельзя просто включить «как есть»: движок asyncpg пулит соединения и привязывает их к event loop, поэтому в `pytest.ini` задан единый session-скоупный loop для фикстур и тестов, а в `tests/conftest.py` общая очистка глобальной БД идёт через `TRUNCATE ... RESTART IDENTITY CASCADE` — обычный `DELETE` по таблицам упирается в внешние ключи, и модуль падал бы на сиде, оставшемся от соседнего.

### Сквозной прогон на тестнете

`scripts/e2e_testnet.py` прогоняет полный контур против **живого** testnet-блока, вызывая реальные функции движка (watcher, закрытие дня, диспетчер выплат, зеркало казны) — кроме бота Telegram: `stake → подсчёт → выплата → зеркало «в ноль»`. Это не локальный тест: ставка делается настоящим переводом с кошелька игрока, приз уходит обратно в цепочку.

Гейт скрипта не даёт запуститься в неподходящем окружении (`TON_NETWORK=mainnet`, нет тестнет-ключей, нет игрока) — он перечислит недостающее и завершится с кодом 2. Необходимы выделенный testnet-контур (свои `TREASURY_TESTNET_ADDRESS`/`TREASURY_TESTNET_MNEMONIC`, `OWNER_WALLET_ADDRESS`), игрок в `players` с верифицированным кошельком и его мнемоника:

```powershell
$env:E2E_PLAYER_ID="…"; $env:E2E_PLAYER_MNEMONIC="…"
python scripts/e2e_testnet.py check     # гейт + диагностика казначея
python scripts/e2e_testnet.py full      # все фазы по порядку (перезапускаемо)
```

В pytest живой e2e-тест помечен маркером `e2e` и **скапывается** без явного флага; включение — `E2E_TESTNET=1` вкупе с полным набором ключей. Охранный гейт при этом покрывается юнит-тестами `tests/test_e2e_testnet_guard.py` в каждом обычном прогоне, без сети.

### Готовность к mainnet

Переключение `TON_NETWORK=mainnet` заблокировано до закрытия must-fix пунктов
(гонка при деплое, безопасность казны, комиссии выплат, миграция данных,
процедура отката). Полный чек-лист с процедурами и журналом инцидентов —
`docs/MAINNET_READINESS.md`. Пока в нём есть хоть один неотмеченный пункт,
переключать сеть нельзя.

### Pre-commit хук на утечку секретов

`scripts/hooks/check_secrets.py` блокирует коммиты с подозрительными строками:
24-словные BIP-39 мнемоники, 64-hex ed25519 приватные ключи. Конфиг — `.pre-commit-config.yaml`.
Подключение на машине разработчика:

```bash
pip install pre-commit
pre-commit install
```

Ручной прогон по всему репозиторию:

```bash
python scripts/hooks/check_secrets.py --all
```

Что НЕ ловит (намеренно): публичные TON-адреса (`0:<hex64>`, `EQ…`/`UQ…`), tx-hash,
короткие hex-идентификаторы, base64-фрагменты в docstring'ах. Регрессии покрывает
`tests/test_pre_commit_secrets.py` (8 проверок: позитивные + негативные).
