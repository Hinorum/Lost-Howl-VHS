## Порядок обновления пин-файла зависимостей

Контроль артефактов (`requirements-critical-hashes.txt`) проверяется в CI и в
сборке на деплое. Он ломает автоматику только в одном месте, и это сделано
сознательно:

**PR от Dependabot, бампящий `pytoniq` или `pytoniq-core`, упадёт в CI** —
пин-файл ещё не обновлён. Дальше:

```
python -m scripts.dependency_hashes --write
git add requirements-critical-hashes.txt && git commit
```

Одна строка ручной работы. Эти два пакета и так уже вынесены в отдельную группу
`ton-side` **без авто-мержа**, то есть ровно для них ревью обязательно. Остальные
группы (`core-deps`, `dev-and-tooling`) не затронуты: их бампы проходят на автоматике
без единого ручного шага.

Проверка молчит только об одном: если сеть недоступна, она **падает**, а не
пропускает. Иначе подмена прошла бы как успешная проверка ровно тогда, когда сеть
легла.

### H1. `misfire_grace_time` не задан
`app/scheduler.py`

Дефолт APScheduler — 1 секунда. Любой запуск с задержкой больше секунды
отбрасывается одним `WARNING`. Под ударом ежедневный `pg_dump` в 04:17 и
`vote-reminder` в 10:00 UTC, ровно на границе 15-секундной сетки тиков.
Постоянного jobstore нет — состояние в RAM, догоняющего запуска тоже нет.

- [x] `misfire_grace_time` на все задачи
- [x] Проверить, что `db-backup` и `vote-reminder` переживают задержку

### H2. Бэкапы: нет мониторинга и не проверено восстановление
`app/ops.py`, `app/backups.py`

`check_anomalies` не знает про бэкапы. Если `pg_dump` сломается, крон
промахнётся (H1) или workflow отключится — никто не узнает. Восстановление
ни разу не отрабатывало: для системы с реальными деньгами непроверенный

- [x] `backup:last_ok` в `watcher_state`, алерт «нет успешного бэкапа 26 ч»
- [x] Проверка целостности файла бэкапа после записи

### H3. Легаси-реконсиляция запускается при любом сбое миграции

`alembic upgrade head` не прошёл — рантайм делает `create_all` по живой базе
и `stamp` на якорь, то есть любой сбой миграции на alembic-базе превращается
в молчаливое расхождение схемы. Привязать к «нет строки `alembic_version`»,
а не к «upgrade упал»; сбой upgrade на alembic-базе — аварийный останов.

- [x] Проверка наличия `alembic_version` вместо проверки кода возврата
- [x] Тест: база с историей и сломанной миграцией → отказ, а не `stamp`

### H4. Откат батча списывает `attempts` у неотправленных строк

- [x] Откат `attempts` при откате хвоста батча

### H6. Авто-возврат без лимитов
`app/ton_watch/refunds.py`

Любой входящий перевод ≥ `refund_min_gram` и младше 14 дней, не ставший
ставкой, создаёт реальную исходящую выплату. Нет ни лимита на отправителя,
ни дневного потолка, ни паузы. Спам мелких переводов → тысячи исходящих tx
и сжигание газа казны.

- [x] Потолок на отправителя и общий; при превышении — `in:refund_cap_*` и ручной разбор
- [x] Метки `ledger:*` / `refund:*` чистятся еженедельной уборкой `ws-cleanup`

Про метки — важная поправка к самому себе. Пункт был записан открытым с
мыслью «нужна отдельная таблица с TTL». Это было неверно: `refund:%` и
`ledger:%` уже стоят в списке префиксов `ws-cleanup` (`app/scheduler.py`), то
есть рост таблицы ограничен неделей, и никакой миграции не требуется.

Проверено, почему снос метки безопасен — метка нужна только на момент обработки,
а не постоянно:

* `_ledger_incoming` / `_ledger_stuck_incoming` / `_record_bank_credit` сначала
  ищут `Income` по `unit_ref == tx_hash` и выходят, если строка есть;
* `_stash_refund` сначала проверяет `Stake` по `tx_hash`, потом `Income` по
  `unit_ref`, потом `Payout` с `kind=refund` по `tx_hash` — и только потом
  берёт метку;
* `claim_once` работает в одной транзакции с самой записью, поэтому «полу-меток»
  не бывает: откат убирает и метку, и строку.

Значит после коммита метка избыточна: настоящий дедуп — это строка `Income` или
`Payout`. Это же переживает и повторное чтение истории при сбросе курсора
(окно 14 дней больше недели уборки): возврат ловится проверкой `Payout` по
`tx_hash`, пыль и «перешагнувший потолок» — проверкой `Income`. Инвариант
«тишина = перевод потерялся» держится на строках `Income`, а не на метках.

Закреплено тестом `test_dedupe_markers_are_redundant_after_their_row_exists`.
